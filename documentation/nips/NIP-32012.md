NIP-32012
=========
Trust Subject Bloom Filter
---------------------------

`draft` `optional` `author:Vision_DWoT` `author:Keutmann`

## Abstract

This NIP defines a standard for **trust subject bloom filter** events (kind `32012`) that allow clients to quickly check whether a given **author** has published a trust event (e.g. [NIP-32010](documentation/nips/NIP-32010.md)) for a given **subject** in a given context, without fetching all of the author's trust events or polling every author's fetch URL. The author (or a third party) publishes a replaceable event containing a **bloom filter** of subject identifiers — each identifier is the SHA256 hash of the trust event's d-tag value. A client tests a subject (and context) by hashing the same d-tag string and querying the filter; a "definitely not" means no such trust event exists; a "might be present" means the client may then query relays or an optional fetch URL to retrieve the actual event(s). This reduces load and avoids slow per-author fetch URL polling.

## Motivation

Knowing whether a **trusted author** has trusted a **specific subject** is useful for building reputation or trust graphs. An author may have published a **huge number** of trust events; downloading all of them is often not practical or desirable. This is especially true for **non‑npub subjects** such as software hashes, article URLs, book identifiers, or other NIP‑73 external IDs: a single trusted maintainer might sign trust events for millions of content items, but clients should not have to download all of those events just to check a few subjects. If the trust event is missing from relays or not yet synced, the client would otherwise have to ask every trusted author's fetch URL or pull full histories, which is slow and does not scale. **The bloom filter** solves this: the author (or a third party) publishes one replaceable event per author (and optional kind/context) that summarizes the set of subjects they have published trust events for in a compact form. Clients can do a fast local membership test without downloading all events; only when the filter suggests a match do they need to fetch from relays or the optional fetch URL. The bloom filter has no false negatives (for the set at publish time) but may have false positives; when the client needs the actual trust data, it MUST fetch and verify the event(s). Bloom filters are particularly effective when the author trusts many **content subjects** (hashes, URLs, NIP‑73 IDs) and comparatively fewer npub identities.

## Specification

### Trust Subject Bloom Filter (Kind `32012`)

The Trust Subject Bloom Filter is a **Parameterized Replaceable Event** (kind `32012`). The event is keyed by the `d` tag in the same format as [NIP-32011](documentation/nips/NIP-32011.md): **npub** (the **author** whose trust events are summarized), a required **kind**, and optional **context**, with an additional optional **value** segment. The event's `content` holds the bloom filter bit array, base64-encoded. A single **`bloom`** tag carries the algorithm **type** and type-specific parameters so clients know how to decode and query. **Anyone** may publish a 32012 for any author; a required `p` tag carries the author's pubkey in **hex** form. The most reliable filter is one published by the author themselves (event `pubkey` equals the hex key in `p`, which corresponds to the npub in `d`).

#### Format

*   **`kind`**: `32012`
*   **`content`**: **Required.** The bloom filter's **bit array**, serialized as **base64** (standard base64 encoding). The decoded bytes represent the raw bits of the filter. The size (how many bits are significant) is given by the **`bloom`** tag parameters for the chosen type (e.g. first numeric param for `sha256-double`). Padding: the bit array length in bytes is `ceil(m / 8)`; base64 encoding may add padding so the string is valid.
*   **`tags`**:
    *   `["d", "<calculated_id>"]`: **Replaceable identifier** for this trust assertion (same `kind`, author `pubkey`, and `d` value (`d = <trust_kind>|<hex(64)>[|context]`) define one addressable slot per [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md)). The `d` value is **machine-oriented** (fixed-length hex where possible); it is **not** NIP-19 (`npub` / `note` / `nevent` / `naddr`). Subject tags carry the **canonical** values (hex pubkey, hex event id, URL, etc.). See **[`d` tag derivation](#d-tag-derivation-replaceable-identifier)** below.

    *   `["d", "<identifier>"]`: **Required.** Same base format as [NIP-32011](documentation/nips/NIP-32011.md), extended with an optional **context** and optional **value** segment: `<trust_kind>|<hex(64)>[|context][|value]`. When the value segment is present and non-empty, it indicates **which trust values the bloom filter covers** (for NIP-32010 typically `"1"` for trusted-only, `"0"` for neutral-only, `"-1"` for distrusted-only). The value is treated as an **opaque string** so that other kinds and value semantics can reuse the same pattern. Clients MUST use the exact `d` string when querying. When a value segment is present but no context is intended (global scope), the context segment MUST still be present as an empty string, e.g. `32010|<pubkey>||1`.
    *   `["t", "<trust_kind>"]`: **Required (for kind filtering).** `t` MUST equal the `<trust_kind>` prefix segment used in the `d` tag value (`d = <trust_kind>|<hex(64)>[|context]`). Clients MUST filter by `#t` to retrieve only events for a specific trust kind, since relay filters do not provide reliable substring/prefix matching on `d`.
    *   `["p", "<pubkey_hex>"]`: **Required.** The author's pubkey in **hex form** (64‑character lowercase hex). It MUST match the `<hex(64)>` segment in `d`.
    *   `["c", "<context>"]`: **Required when context is non-empty in `d`.** Context scope (same semantics as [NIP-32010](documentation/nips/NIP-32010.md)). MUST match the context segment in `d`.
    *   `["v", "<value>"]`: **Required when the value segment is non-empty in `d`.** Encodes the value that this filter is valid for (for NIP-32010 typically `"1"`, `"0"`, or `"-1"`). MUST match the value segment in `d` when present. The value is a free-form string so that other kinds can define their own value semantics.
    *   `["bloom", "<type>", "<param1>", "<param2>", ...]`: **Required.** Single tag. Encodes the bloom filter **algorithm type** and type-specific parameters so clients know how to decode `content` and test membership.
        *   **&lt;type&gt;:** Algorithm identifier (e.g. `sha256-double`). Defines how the subject hash is computed and how indices into the bit array are derived. Clients that do not support the given type MAY ignore the event or treat it as unsupported.
        *   **Remaining elements:** Type-specific parameters (order and meaning defined per type). See **Algorithm types** below.
    *   `["relay", "<url>"]`: **Optional.** Multiple allowed. Relay URLs where the author's trust events can be found. Clients MAY query these when the filter returns "might be present."
    *   `["fetch", "<url>"]`: **Optional.** Single tag. Base URL of an HTTP API (not a Nostr relay) to fetch events by subject or range; same concept as in [NIP-32011](documentation/nips/NIP-32011.md). Query parameters (e.g. kind, context, subject or event id) are implementation-defined; see NIP-32011 for a suggested pattern.

#### Algorithm types

The **`bloom`** tag's first value is the **type**. Only types known to the client can be used for querying; unknown types leave the spec open for future algorithms.

*   **`sha256-double`** (recommended): Subject identifier = SHA256(d-tag value). Indices into the bit array are derived by double hashing (e.g. from the 256-bit hash, produce `nf` indices in `[0, m)`). **Parameters:** second = size in **bits** (m), third = **number of hash functions** (nf). Example: `["bloom", "sha256-double", "4096", "10"]`.
*   **Other types:** MAY be defined in extensions or future NIPs. Clients that do not recognize `<type>` SHOULD skip the event or treat it as unsupported. New types use the same tag shape: `["bloom", "<type>", ...]` with type-specific parameters.

#### Subject identifier (what goes into the filter)

For each summarized trust event (e.g. kind 32010), the **unique identifier** is that event's **full d-tag value string** (see [NIP-32010](documentation/nips/NIP-32010.md) [`d` tag derivation](documentation/nips/NIP-32010.md#d-tag-derivation-replaceable-identifier): 64-hex fragment(s), XOR of **deduplicated** unique fragments for multi-subject batches, optional `|<context>` suffix — hash the **exact** `d` string as it appears on the wire). When the `d` identifier in the 32012 event includes a value segment (fourth segment), the publisher MUST include **only events whose value matches that segment** when populating the bloom filter. A typical pattern for NIP-32010 is to define separate bloom filters for `"1"`, `"0"`, and `"-1"` so that clients can, for example, test \"trusted content\" and \"distrusted content\" independently. To obtain a uniform fixed-size input for the bloom filter, the publisher and the client use:

**subject_hash = SHA256(d_tag_value)**

with the d-tag value encoded as a canonical string (e.g. UTF-8). The bloom filter stores membership of these **subject_hash** values (one per trust event, by d-tag). So the filter answers: "has the author published a trust event whose d-tag hashes to this value?" — which corresponds to "has the author trusted this subject (and context)?" when the client builds the same d-tag string for the subject and context they care about.

#### Bloom filter algorithm (type `sha256-double`)

For type **`sha256-double`**, the algorithm is as follows. Other types define their own insertion and query rules.

*   **Insertion (publisher):** For each trust event, compute `d_val` = that event's d-tag value string, then `h = SHA256(d_val)`. Add `h` to the bloom filter using `nf` hash functions: derive `nf` indices in the range `[0, m)` via double hashing (e.g. h_0 = hash(h || 0) mod m, h_1 = hash(h || 1) mod m, ...). Set those bits to 1 in the bit array. Encode the bit array (e.g. as bytes, MSB first per byte) and then base64-encode for `content`.
*   **Query (client):** Given a subject and context, build the d-tag string that a 32010 event would have for that (subject, context) per NIP-32010. Compute `h = SHA256(d_tag_string)`. Using the same m and nf from the `bloom` tag, compute the same indices and check whether all corresponding bits are 1. If any bit is 0, the element is **definitely not** in the set (no false negatives). If all are 1, the element **might be** in the set (possible false positive); the client SHOULD fetch from relays or the fetch URL to obtain the actual event(s) and verify.

#### Building the filter (publisher)

1.  Collect all events from the author for the chosen kind (default 32010) and context (if scoped).
2.  Choose a bloom **type** (e.g. `sha256-double`) and parameters (e.g. m, nf). Allocate a bit array of length m (bits), all zeros.
3.  For each event: `d_val` = event's d-tag value; `h = SHA256(d_val)`; compute indices from `h` per the chosen type; set those bits to 1.
4.  Encode the bit array as base64 and set event `content`. Set the **`bloom`** tag (e.g. `["bloom", "sha256-double", "<m>", "<nf>"]`) and optionally `relay`, `fetch`.

#### Example JSON (minimal, self-published)

```json
{
  "kind": 32012,
  "pubkey": "<32-bytes lowercase hex of the event creator>",
  "created_at": 1738368000,
  "content": "AAAAAAAABQAAAAAAAACAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA==",
  "tags": [
    ["d", "<kind>|<64-hex pubkey>|development|1"],
    ["p", "<64-hex pubkey of the pubkey in d>"],
    ["bloom", "sha256-double", "1024", "7"]
  ]
}
```

#### Example JSON (with kind, context, relay, fetch)

```json
{
  "kind": 32012,
  "pubkey": "<32-bytes lowercase hex of the event creator>",
  "created_at": 1738368000,
  "content": "<base64_bloom_bits>",
  "tags": [
    ["d", "<kind>|<64-hex pubkey>|development|1"],
    ["t", "<kind in the d tag>"],
    ["p", "<64-hex pubkey of the pubkey in d>"],
    ["c", "development"],
    ["bloom", "sha256-double", "4096", "10"],
    ["relay", "wss://relay.example.com"],
    ["fetch", "https://example.com/trust/events"]
  ]
}
```

## Client Behavior (Recommendation)

### 1. Membership checks for a single author

1.  **Fetch bloom filter event:** Query for `kinds: [32012]`, `#d: [<d_value>]` where `d_value` is the author pubkey (and optional `kind|<pubkey>|context` as needed).
2.  **Parse bloom tag:** Read the **`bloom`** tag. The first value is the **type**. If the client does not support this type, skip the event or treat as unsupported. Otherwise parse type-specific parameters (e.g. for `sha256-double`: second = m, third = nf). Decode `content` from base64 to a bit array; use the type's first size parameter (e.g. m) to determine how many bits are significant.
3.  **Check subject:** To ask "has author I trusted subject S in context C?", build the d-tag string that a 32010 event would have for (S, C) per NIP-32010. Compute `h = SHA256(d_tag_string)`. Using the same type and parameters, compute the indices and test the bits. If any bit is 0, the author has **not** published such a trust event. If all are 1, the author **might** have; fetch from `relay` tags or `fetch` URL (with kind/context/subject or event id as needed) to retrieve and verify the actual event(s).
4.  **False positives:** The bloom filter may yield false positives. When the client needs the actual trust value or event, it MUST fetch and verify; it MUST NOT rely on a positive filter result alone.

### 2. Using bloom filters in graph-based subscription

When performing graph-based trusted-author subscriptions as described in NIP-32011, clients MAY use 32012 bloom filters to decide **which subjects are worth following up on**:

1.  For each author in the graph frontier (root author or trusted neighbor), fetch its 32012 bloom filter for the desired kind/context (same `d` format as NIP-32011).
2.  Before opening additional relay subscriptions for that author, use the bloom filter to test whether there is any trust for the subjects of interest (e.g. candidate authors for the next depth). If the filter says **definitely not**, the client can skip fetching full events for that (author, subject, context) pair.
3.  If the filter says **might be present**, the client MAY then query relays (using a selective subscription helper such as `startAuthorGraphSubscription`) or an HTTP `fetch` URL to retrieve the relevant events.
4.  This allows large trust graphs to be explored while still constraining relay traffic to those (author, subject, context) combinations that are likely to exist.

## Security Considerations

*   **Who may publish:** Anyone may publish a kind 32012 event for any npub (author). Self-published (event `pubkey` == author) is most reliable; third-party filters may be incomplete or wrong. Trust is left to the client.
*   **Probabilistic:** The bloom filter has no false negatives for the set at publish time but may have false positives. Clients MUST confirm by fetching the actual event(s) when they need trust data; they MUST NOT treat a positive filter result as proof of trust.
*   **Staleness:** The filter is as of publish time. New trust events require a new 32012; until then, new subjects are not reflected.
*   **Fetch URL:** Optional and not a substitute for verification; clients MUST verify event signatures.

## Optional / Future Extensions

*   **Other event kinds:** If the `k` tag is used for kinds other than 32010, the same hashing rule (SHA256 of that kind's d-tag or equivalent identifier) can be applied.
*   **New bloom types:** Additional algorithm types (e.g. different hash or index derivation) can be added by defining a new `<type>` string and its parameter list; the single `bloom` tag format remains the same.
