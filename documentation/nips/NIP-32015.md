NIP-32015
=========
Subject Confirmation
---------------------------

`draft` `optional` `author:Vision_DWoT` `author:Keutmann`

## Abstract

This NIP defines **subject confirmation** events (kind `32015`). An author **acknowledges** that a **subject** (same subject types as [NIP-32010](documentation/nips/NIP-32010.md)) is the entity they intend to refer to in a given **context** — **not** that the subject passed independent **validation**, **verification**, or **trust**. It is a **lightweight boolean attribute** (“this is the thing I mean”), distinct from [NIP-32010](documentation/nips/NIP-32010.md) **trust** and from cryptographic proofs (e.g. NIP-05). Clients **MUST NOT** use kind **`32015`** to **expand** t1 **trust-graph** traversal from the subject. There is **no** **`t`** tag: these events **annotate the subject** directly; **`t`** is reserved for kinds that **index or augment** another kind (e.g. [NIP-32011](documentation/nips/NIP-32011.md) / [NIP-32012](documentation/nips/NIP-32012.md) / [NIP-32013](documentation/nips/NIP-32013.md)). Discovery uses **`kinds: [32015]`** (and **`#d`** / subject filters as needed).

## Motivation

Not every assertion needs a **trust** edge or a **rating**. Sometimes an author only wants to signal **recognition** or **acknowledgment** of a subject (e.g. “this pubkey is the account we coordinate with for this campaign”) without vouching for competence or honesty. **Confirmation** fills that role without overloading **`32010`** or implying graph hops.

## Specification

### Confirmation Event (Kind `32015`)

Kind **`32015`** is a **Parameterized Replaceable Event** per [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md). **One subject per event.** The replaceable **`d`** uses the same **`d_base[|context]`** derivation as [NIP-32010](documentation/nips/NIP-32010.md) for that subject.

#### Format

*   **`kind`**: `32015`
*   **`content`**: Optional. Clarifying note (e.g. why the subject is acknowledged). SHOULD NOT exceed **1024 characters**.
*   **`tags`**:
    *   `["d", "<d_base>[|context]"]`: **Required.** Per [NIP-32010](documentation/nips/NIP-32010.md) [`d` tag derivation](documentation/nips/NIP-32010.md#d-tag-derivation-replaceable-identifier) for **one** subject.
    *   `["confirmed", "<bool>"]`: **Required.** **`true`**, **`false`**, or an **empty string** (lowercase for booleans). **`true`** — the author **confirms** the subject for this slot; **`false`** — explicitly **withdraws** a prior confirmation (replaceable update). **`""`** — **tombstone**: clients **MUST** treat the replaceable slot as **cleared** (see [Tombstone (empty confirmed)](#tombstone-empty-confirmed)).
    *   `["c", "<context>"]`: **Optional; at most one.** Same semantics as [NIP-32010](documentation/nips/NIP-32010.md); MUST align with **`d`** when a non-empty context is used.
    *   `["x", "<unix_timestamp>"]`: **Optional; at most one.** **Activate** — Unix timestamp (seconds). The confirmation is valid for resolution only when the current time is **≥** this value. Same semantics as [NIP-32010](documentation/nips/NIP-32010.md) **`x`**. Omit if it applies immediately.
    *   `["y", "<unix_timestamp>"]`: **Optional; at most one.** **Expire** — Unix timestamp (seconds). The confirmation is valid for resolution only when the current time is **≤** this value. Same semantics as [NIP-32010](documentation/nips/NIP-32010.md) **`y`**. Omit if it does not expire.
    *   **Subject tags (exactly one required):** **`p`**, **`e`**, **`a`**, **`h`**, **`r`**, or **`i`** (+ **`k`** as required by NIP-73), with NIP-32010 canonical values for **`d`**.

**Normative tag ordering:** **`d`**, **`confirmed`**, optional **`c`**, optional **`x`**, optional **`y`**, subject tag(s), optional **`k`** after **`i`** per NIP-32010 conventions.

#### Semantics

*   **Confirmation is not validation:** The author does **not** assert that a name, domain, or key ownership was **cryptographically** proven — only that **they** treat this subject as **the** referent in this context.
*   **Not trust:** **`confirmed: true`** MUST NOT be interpreted as [NIP-32010](documentation/nips/NIP-32010.md) **`v` = `1`**.

#### Tombstone (empty confirmed)

Publishing a replaceable update whose **`confirmed`** value is the **empty string** clears that author’s **`32015`** slot for the same **`d`**. Clients **MUST** treat the slot as **absent** in resolved subject attributes — **removed from the resolved graph**.

#### Verification

1.  Exactly **one** subject tag; **`d`** MUST match NIP-32010 derivation for that subject and context.
2.  **`confirmed`** MUST be the string **`true`**, **`false`**, or **`""`**. If **`confirmed`** is empty, the event is a **tombstone**; do **not** require boolean semantics beyond clearing the slot.
3.  If **`x`** and/or **`y`** are present, each value MUST parse as a non-negative integer (Unix seconds). If **both** are present, **`x`** SHOULD be **≤** **`y`**.

## Relationship to NIP-32010

| Kind     | Role |
|----------|------|
| **`32010`** | Tri-state **trust**; **may** drive **t1** graph expansion. |
| **`32015`** | Boolean **acknowledgment** only; **no** graph expansion. |

## Client behavior (recommendation)

1.  Show confirmations as **badges** or **metadata**, not as trust edges.
2.  **Do not** traverse into neighbors based on **`32015`** alone.
3.  **Validity window:** Apply **`x`** / **`y`** like [NIP-32010](documentation/nips/NIP-32010.md) (now **≥** **`x`** if **`x`** present; now **≤** **`y`** if **`y`** present). **Tombstones** (**empty** **`confirmed`**) clear the slot regardless of **`x`**/**`y`**.
4.  **Latest wins** per replaceable slot for the same **`d`**. If the latest event has an **empty** **`confirmed`**, the slot contributes **nothing** to resolved subject attributes.

## Example JSON

```json
{
  "kind": 32015,
  "pubkey": "<64 lowercase hex chars — author; NIP-01>",
  "created_at": 1738368000,
  "content": "This is the project lead pubkey for the grant program.",
  "tags": [
    ["d", "<64 lowercase hex — NIP-32010 d_base for this subject>|grants"],
    ["confirmed", "true"],
    ["c", "grants"],
    ["x", "1672531200"],
    ["y", "1704067200"],
    ["p", "<64 lowercase hex — subject pubkey>"]
  ],
  "sig": "<author signature>"
}
```

(Optional **`x`** / **`y`** bound when the confirmation applies; omit either side for no bound on that side.)

#### Example JSON (tombstone — clear slot)

```json
{
  "kind": 32015,
  "pubkey": "<64 lowercase hex chars — author; NIP-01>",
  "created_at": 1738444400,
  "content": "",
  "tags": [
    ["d", "<same d as the confirmation being removed>"],
    ["confirmed", ""],
    ["p", "<64 lowercase hex — subject pubkey>"]
  ],
  "sig": "<author signature>"
}
```

## Security considerations

*   **Misleading UI:** Clients MUST NOT label confirmation as “verified” or “trusted” without separate evidence.
*   **Spam:** Confirmations are cheap; feeds MAY rate-limit or filter by graph distance from the user.
