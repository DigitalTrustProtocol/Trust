# NIP-32010

## Digital Web of Trust Reputation (Trust)

`draft` `optional` `author:Vision_DWoT` `author:Keutmann`

## Abstract

This NIP defines a Nostr event for saying, "I trust this subject", "I cancel my previous trust statement", or "I distrust this subject".

The event kind is `32010`. It is an addressable event, because it is in the Nostr `30000`-`39999` range. A new event from the same author with the same `d` tag replaces the older one.

Kind `32010` is the base profile for directed trust graphs. In path-based trust resolution, a positive trust statement to a `p` subject can be used as the next hop.

Kind `32010` stores trust inputs, not final reputation outputs. Final reputation is computed later by each client or service using its own policy and selected event set.

## Motivation

Nostr already has a follow list in kind `3`. This is treated as **social trust**: it says who someone wants to follow, read, or stay connected to. Social trust is useful, but it is not the same as saying, "I trust this person for this purpose." A person may follow a news source, a celebrity, or a company account without trusting that account for payments, moderation, software, or safety.

A direct trust is needed because trust decisions in open networks require a clear, interoperable signal that is explicit, directional, and machine-readable. Without a dedicated trust event, clients must guess trust from weak signals (follows, likes, engagement counts), which causes inconsistent behavior across apps and makes it harder to warn about harmful actors.

Kind `32010` is **directed trust**. It is an explicit statement from one author to a specific subject, optionally in a specific context:

1. It separates attention from trust.
2. It lets trust be scoped to a context, such as `development`, `security`, or `commerce`.
3. It supports distrust without needing a central blocklist.
4. It can describe trust in people, events, hashes, URLs, and external identifiers.
5. Trust is subjective, so the most common explicit values are `1` (trust) and `-1` (distrust). The `0` value exists mainly to cancel a previous statement.

## Relationship to NIP-85

[NIP-85](https://github.com/nostr-protocol/nips/blob/master/85.md) defines **Trusted Assertions**. In particular, NIP-85 kind `30382` lets a trusted service publish information about a user, such as `rank`.

In this document, NIP-85 is treated as **directed trust** mainly when it publishes evaluative trust outputs like `rank`.

One limitation of `rank` is that it is usually published as a non-negative value (for example `0-100`) and does not express a direct negative trust state. This can push trust game dynamics in a positive-only direction, which weakens explicit warning signals. In NIP-32010, rank-like scoring is treated as complementary context, while the core trust signal stays the clean, explicit statement: `1`, `0` (cancel), or `-1`.

Key differences between NIP-85 and NIP-32010:

- **Ternary vs rank:** NIP-85 commonly publishes `rank` values (for example `0-100`). NIP-32010 publishes explicit trust ternary value: `1` (trust), `0` (cancel), `-1` (distrust).
- **Single-target output vs multi-subject statement:** NIP-85 `30382` is usually consumed as one result about one target user. NIP-32010 can point to one or many subjects in the same event (for example, one `-1` event for several spam pubkeys).
- **No trust context model vs context-driven trust model:** NIP-32010 has a `c` context that allows trust to be scoped by where/what/state.
  - **Where:** `commerce:p2p`, `nostr:moderation`
  - **What:** `development`, `security_audit`
  - **State:** time/state-like scopes such as `incident:active`, `incident:resolved`

This context model lets one author trust and distrust the same subject in different scopes (for example, trust in `development` but distrust in `commerce:p2p:incident:active`).

A client may use both. For example, a client could use NIP-32010 events to build a local trust graph and also display NIP-85 `30382:rank` values from selected service providers.

Kind `3` remains useful as social trust, but clients SHOULD NOT treat a follow as the same thing as a NIP-32010 trust statement or a NIP-85 trusted assertion.

## Specification

### Trust Event (Kind `32010`)

Kind `32010` is an addressable event. It can point to:

- a Nostr identity, using a `p` tag;
- a Nostr event, note, profile, address, pubkey reference, hash, URL, or external identifier, using an `i` tag.

### Format

- `**kind`**: `32010`
- `**content**`: Optional. A short human-readable reason for the trust statement, such as `"Audited their code"` or `"Known scammer"`. It SHOULD NOT exceed 1024 characters. Use a URL or another Nostr event for long explanations.
- `**tags**`:
  - `["d", "<id>"]`: Required. The replaceable identifier for this trust statement. See [Building the `d` tag](#building-the-d-tag).
  - `["p", "<pubkey>"]`: Subject is a Nostr pubkey. The value MUST be 64 lowercase hex characters. One or more `p` tags are allowed.
  - `["i", "<typed_subject_id>"]`: Subject is anything that is not directly represented by a `p` tag. One or more `i` tags are allowed.
  - `["c", "<context>"]`: Optional. The context where this trust applies. The context model is typically expressed as **where / what / state** (for example `commerce:p2p`). Use `""` or omit the tag for general trust.
  - `["v", "<value>"]`: Required. The trust value. It MUST be `"1"`, `"0"`, or `"-1"`.
  - `["x", "<unix_timestamp>"]`: Optional. Activate time. The event applies only when the current Unix time is greater than or equal to this value.
  - `["y", "<unix_timestamp>"]`: Optional. Expire time. The event applies only when the current Unix time is less than or equal to this value.

At least one subject tag, either `p` or `i`, is required.

### Subject Tags

The subject is what the author is trusting or distrusting.

#### `p` subject

Use `p` for a Nostr identity:

```json
["p", "<64 lowercase hex pubkey>"]
```

Positive `p` trust (`v = "1"`) is the normal graph edge for t1 path expansion.

#### `i` subject

Use `i` for typed subject identifiers:

- `nostr:event:<value>` for a Nostr event id when the event kind is not important.
- `nostr:note:<value>` for a note event.
- `nostr:profile:<value>` for a profile reference.
- `nostr:pubkey:<value>` for a pubkey reference stored as an `i` subject.
- `nostr:addr:<value>` for an addressable event.
- `hash:<64-lowercase-hex>` for a content hash.
- `web:<normalized-url>` for a web resource.
- `ext:<external-content-id>` for a [NIP-73](https://github.com/nostr-protocol/nips/blob/master/73.md) external identifier.

For `nostr:*` values, implementations MAY accept either 64-hex values or matching NIP-19 encodings when available, but they SHOULD normalize them before building `d`.

`nostr:pubkey:<value>` identifies a pubkey for scoring, but it is not a t1 graph-expansion edge. Use a `p` tag when the assertion should be usable as a graph edge.

#### Legacy tags

Implementations MAY accept old subject tags such as `e`, `a`, `h`, and `r` when importing older data. They SHOULD normalize those subjects to `i` before validation, storage, or graph processing.

### Trust Values (`v` tag)

The `v` tag uses a small three-value ternary scale:

- `**"1"`: Trust.** The author vouches for the subject in this context.
- `**"0"`: Cancel/revoke previous statement.** The author clears their previous trust or distrust statement for this same slot. Clients SHOULD treat this as removing the edge from the resolved graph.
- `**"-1"`: Distrust.** The author warns against the subject in this context.

Publishing `v = "0"` as a first-ever statement for a slot has no practical effect on the graph.

### Contexts (`c` tag)

Trust is often specific. A person may be trusted for software review but not for medical advice.

The `c` tag names the context. A practical model is **where / what / state**:

- **Where** (domain or place): `commerce`, `commerce:p2p`, `nostr:moderation`
- **What** (activity or capability): `development`, `security_audit`, `transport:driving`
- **State** (current phase or condition): `incident:active`, `incident:resolved`, `review:pending`

These can be combined as one context path, for example:

- `commerce:p2p`
- `review:pending`
- `incident:resolved`

Contexts MAY use colon-separated levels from broad to specific. The empty context (`""`) or missing `c` tag means general trust.

When resolving trust for a requested context, clients SHOULD use these rules:

1. Use the most specific matching statement from the same author and subject.
2. If there is no exact match, the nearest parent context may apply.
3. If no scoped context applies, the general context may apply.
4. If the same author publishes more than one statement for the same subject and same context, the newest valid event wins.

Example: an author may trust Bob generally, trust Bob in `development`, and distrust Bob in `commerce`.

## Building the `d` tag

The `d` tag identifies the replaceable slot. It MUST be stable: the same author, same subjects, and same context produce the same `d`.

The shape is:

```text
d = <base_id>
d = <base_id>|<context>
```

Use the second form only when the context is non-empty. The context part MUST exactly match the `c` tag.

### Step 1: Normalize each subject

Scan the event tags from first to last. Each `p` or `i` tag adds one subject to the ordered subject list.

For each subject, build its normalized subject string:


| Tag | Subject        | Normalized subject string                                                                              |
| --- | -------------- | ------------------------------------------------------------------------------------------------------ |
| `p` | Nostr identity | The 64 lowercase hex pubkey from the `p` tag.                                                          |
| `i` | Typed subject  | The full normalized `i` value, such as `nostr:note:<value>`, `hash:<hex>`, `web:<url>`, or `ext:<id>`. |


### Step 2: Turn each subject into a 64-hex id

For each normalized subject string:

- If it is exactly 64 hex characters, lowercase it and use it directly.
- Otherwise, UTF-8 encode the string, hash it with SHA-256, and lowercase the 64-hex result.

This means a single `p` subject uses the pubkey itself as `base_id`.

### Step 3: Combine multiple subjects

If the event has one subject, that subject id is `base_id`.

If the event has multiple subjects:

1. Remove duplicate subject ids while keeping the first occurrence.
2. Decode each remaining 64-hex id into 32 bytes.
3. Combine the byte arrays with byte-wise XOR.
4. Encode the result as 64 lowercase hex. That result is `base_id`.

Duplicate subjects MUST NOT be combined more than once. Repeating the same subject must produce the same `base_id` as listing it once.

### Step 4: Add context

If the context is missing or empty:

```text
d = <base_id>
```

If the context is non-empty:

```text
d = <base_id>|<context>
```

The context string MUST NOT contain `|`.

### Implementation Checklist

- Use UTF-8 before SHA-256.
- Output lowercase hex.
- Normalize `nostr:*`, `web:*`, and `ext:*` subjects consistently before building `d`.
- Remove duplicate subject ids before combining multiple subjects.
- Verify that the `d` context suffix matches the `c` tag.

## Multiple Subjects (Batch Events)

A single kind `32010` event MAY apply the same trust value, context, content, and time rules to more than one subject.

Example: one author can publish one event that distrusts several spam accounts in the `spam` context.

Rules for batch events:

- The event MUST contain at least one `p` or `i` subject tag.
- The `v`, `c`, `content`, `x`, and `y` values apply to every subject in the event.
- Subject order is the order of `p` and `i` tags on the wire.
- The `d` tag is built from all distinct subject ids as described above.
- Clients MUST resolve the event as separate statements for each subject, even though they share one replaceable slot.

If a later event from the same author changes only one subject from a previous batch, clients still use the latest valid statement for each `(author, subject, context)` pair.

## Time Rules

Time tags limit when the trust statement applies.

- If `x` is present, the event is not active before that Unix timestamp.
- If `y` is present, the event is not active after that Unix timestamp.
- If both `x` and `y` are present, both limits must allow the event.
- If none of these tags are present, the event is always active.

## NIP-73 Integration

[NIP-73](https://github.com/nostr-protocol/nips/blob/master/73.md) defines external content identifiers with `i` and `k` tags.

Kind `32010` uses `i` values with the `ext:` prefix for NIP-73-style external identifiers, for example:

```json
["i", "ext:isbn:9780765382030"]
```

Clients can query kind `32010` events by `#i` to find trust statements for a book, paper, podcast, blockchain transaction, or other external identifier.

The external id SHOULD follow NIP-73 normalization rules, such as lowercase where required and no hyphens for identifiers that require removal.

## Client Behavior (Recommendation)

Clients SHOULD use kind `32010` to build a local trust graph from roots and policy they choose.

- Ingest from authors the user already follows or trusts; ignore events outside `x`/`y` active windows.
- Verify `d` against subjects and context; resolve each `(author, subject, context)` to the newest valid event and apply context fallback as in [Contexts](#contexts-c-tag).
- Use positive `p` trust as graph edges; use `i` for scoring or labels, not path expansion through `i=nostr:pubkey:<value>`.

## Security Considerations

- **Subjective trust:** A kind `32010` graph depends on the viewer's chosen roots and policy. There is no global truth score.
- **Sybil attacks:** Starting from trusted roots can reduce Sybil impact, but it does not remove all risk. Clients should limit path depth and choose roots carefully.
- **Public statements:** Trust and distrust events are public. A `-1` rating is a public statement about the subject.
- **Context matters:** Clients should not treat trust in one context as trust in every context.
- **Service keys:** If a service publishes kind `32010` events, clients should understand what that service claims to measure and should not confuse the service's graph input with a NIP-85 final assertion.
