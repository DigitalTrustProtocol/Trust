NIP-32010
=========
Digital Web of Trust Reputation (Trust)
---------------------------

`draft` `optional` `author:Vision_DWoT` `author:Keutmann`

## Abstract

This NIP defines a standard for expressing **trust assertions** on Nostr using a specialized event kind (`32010`). This kind is the **t1** (base graph-trust) profile: path algorithms **expand** through subjects reached by positive trust in this kind. It allows users to publicly vouch for (or warn against) identities, events, or static content in specific contexts, creating a decentralized, subjective Web of Trust graph.

**Reputation** is not defined by this event; rather, reputation is a subjective score calculated by aggregating these trust events from the perspective of a specific observer.

## Motivation

Current Nostr mechanisms rely primarily on the "follow graph" (Kind 3). While useful for content curation, following someone does not strictly imply *trusting* them (e.g., one might follow a news source for information but not trust them with financial custody).

A dedicated Trust event allows for:
1.  **Explicit Trust Scores:** Differentiating between "following" (attention) and "trusting" (validation).
2.  **Contextual Trust:** Trusting a user for "code review" vs. "medical advice".
3.  **Distrust Signals:** Explicitly warning about malicious actors (-1) without needing a central blocklist.
4.  **Content Trust:** Trusing software binaries, articles, or other static content directly.

## Specification

### Trust Event (Kind `32010`)

The Trust event is a **Parameterized Replaceable Event** (Kind `32010`). It is used to assert trust in **identities** (public keys), **events** (Nostr IDs), **content** (hashes/URLs), or **external content IDs** (per [NIP-73](https://github.com/nostr-protocol/nips/blob/master/73.md)).

#### Format

*   **`kind`**: `32010`
*   **`content`**: (Optional) A human-readable note explaining the reason for the trust assertion (e.g., "Audited their code, LGTM" or "Scammer, do not interact").
    *   **Limit:** The content string should NOT exceed **1024 characters**. This field is for brief context, not full reports. If a detailed explanation is needed, the `content` MAY contain a URL to an external document or another Nostr event.
*   **`tags`**:
    *   `["d", "<calculated_id>"]`: **Replaceable identifier** for this trust assertion. Same **`kind` `32010`**, author **`pubkey`**, and **`d`** value define one addressable slot per [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md). **`d`** MUST be **`d_base`** or **`d_base|context`** as in **[`d` tag derivation](#d-tag-derivation-replaceable-identifier)**. The `d` value is **machine-oriented** (fixed-width subject material). For Nostr references, `i` values are canonicalized as `nostr:<type>:<value>`.
    *   `["c", "<context>"]`: The scope of the trust.
        *   **Specific:** e.g., "development", "trading", "security".
        *   **General:** Use `""` (empty string) or omit the tag entirely for general context trust.
    *   `["v", "<value>"]`: The trust score. Must be one of:
        *   `"1"`: Trust / Vouch / Endorse
        *   `"0"`: Neutral / Unsure / Revoke previous rating
        *   `"-1"`: Distrust / Block / Warn
    *   `["x", "<unix_timestamp>"]`: **Optional.** Single tag. **Activate** — Unix timestamp (seconds). The event is valid for resolution only when the current time is **≥** this value. Omit or leave absent if the trust is valid immediately. Useful for temporary grants, time-bound endorsements, or scheduled activation. Single character `x` allows relay filters (e.g. `#x`) for time-based queries.
    *   `["y", "<unix_timestamp>"]`: **Optional.** Single tag. **Expire** — Unix timestamp (seconds). The event is valid for resolution only when the current time is **≤** this value. Omit or leave absent if the trust does not expire. Useful for temporary access, obsolete information, or time-limited trust. Single character `y` allows relay filters (e.g. `#y`) for time-based queries.
    *   `["z", "<cron_expression>", "<timespan_seconds>"]`: **Optional.** Multiple tags allowed. **Schedule (cron)** — Defines recurring time windows when the trust is valid. First parameter: cron expression (UTC) specifying the **start time** of each window. Second parameter: **timespan** in seconds — the duration each window lasts. The event is valid for resolution when the current time falls within any defined window. Multiple `z` tags allow different time slots (e.g., weekdays 09:00–17:00, Saturdays 10:00–14:00). Useful for granting access in intervals. All times in UTC.
    *   **Subject Tags (One or more required):**
        *   `["p", "<pubkey>"]`: Identity (user). `<pubkey>` MUST be **64 lowercase hex characters** (ASCII text on the wire, encoding the 32-byte secp256k1 x-only pubkey — **not** raw bytes in the tag).
        *   `["i", "<typed_subject_id>"]`: Generic typed subject identifier. This NIP uses `i` for all non-`p` subject kinds.
            *   **Nostr references MUST start with `nostr:`** and include a type segment: `nostr:<type>:<value>`.
            *   Recommended Nostr types include: `event`, `profile`, `pubkey`, `note`, `addr`.
            *   Nostr generic event id (kind unknown): `nostr:event:<value>`
            *   Nostr note event id: `nostr:note:<value>`
            *   Nostr addressable: `nostr:addr:<value>`
            *   For Nostr types, `<value>` MAY be a 64-lowercase-hex id or the corresponding NIP-19 encoding when available (e.g. `npub`, `nprofile`, `note`, `nevent`, `naddr`).
            *   `nostr:pubkey:<value>` identifies the same target as the `p` tag after canonicalization.
            *   Content hash: `hash:<64-lowercase-hex>`
            *   web/resource: `web:<canonical-normalized-url>`
            *   NIP-73 external id: `ext:<external_content_id>` (normalized per [NIP-73](https://github.com/nostr-protocol/nips/blob/master/73.md))
        *   **Compatibility (non-normative):** Implementations MAY accept legacy subject tags (`e`, `a`, `h`, `r`) on ingest, but SHOULD canonicalize them to `i` before validation/storage/graph processing.

#### Multiple subjects (batch)

A trust event MAY assert the **same** trust value, context, and time rules for **more than one** subject in a single event by including **multiple** subject tags. Batch events use **one** replaceable `d` tag for the whole set (see [Step 3 — Combine fragments](#step-3--combine-fragments)).

*   **Semantics:** The optional `content`, required `v`, optional `c`, and optional `x` / `y` / `z` tags apply **uniformly** to **every** subject in the batch. Clients MUST interpret the event as one assertion about the **set** of subjects, not independent assertions per subject.

*   **Building the ordered subject list:** Construct the list `S₁ … Sₙ` by scanning the event’s `tags` array **from first tag to last** (index order). Each tag whose **first element** (tag name) is `p` or `i` **appends** one subject to the list, in that order. **Tag order on the wire is normative** — do not sort by tag name, do not group by type.

*   **Mixed types:** Subjects may be heterogeneous (e.g. several `p` tags, or `p` + multiple `i` types, etc.). Each subject contributes **one** fragment `F` per [Step 1](#step-1--canonical-preimage-string-per-subject) and [Step 2](#step-2--per-subject-fragment-always-64-lowercase-hex-characters). [Step 3](#step-3--combine-fragments) **deduplicates** identical fragments, then XORs the unique set.

*   **`d` for batches:** After computing `F₁ … Fₙ` in wire order, form the **unique** fragment list: keep **at most one** entry per distinct 64-character lowercase hex string (preserve **first-seen** order for the remaining list). `d_base` is that single fragment if only one unique value remains; otherwise the 64-character lowercase hex encoding of the **bitwise XOR** of the 32-byte decodes of **each unique** fragment. The optional context suffix `|C` is unchanged ([Step 4](#step-4--context-suffix)).

*   **Duplicates (anti-fraud):** Implementations MUST **not** XOR duplicate fragments. Repeating the same subject (same fragment `F`) MUST NOT change `d_base` compared to listing that subject once — in particular, `F ⊕ F` MUST NOT be applied (that would cancel to zero and allow a batch `d` to collide with unrelated assertions). Publishers **SHOULD** omit redundant subject tags; verifiers **MUST** still apply deduplication when validating `d`.

*   **Validity:** At least **one** subject tag is required (`n ≥ 1`). There is no separate “batch” kind; batch is simply `n > 1`.

### `d` tag derivation (replaceable identifier)

Implementations MUST compute `d` so that two semantically identical trust assertions (same subjects, same context rules) produce the **same** `d` string. The algorithm is **deterministic** and uses **UTF-8** and **SHA-256** only (no NIP-19 in `d`).

#### Step 1 — Canonical preimage string (per subject)

Each **subject tag** names **what** is being trusted (the trust target). Only these **first-element** names are subject tags: **`p`** and **`i`**.

For **each** subject entry in **wire tag order**, build one UTF-8 string `P` (the **preimage**) from the rules in the **Canonical preimage `P`** column (same canonical values as on the event tags, after normalization):

| Tag | Identifies (role) | Canonical preimage `P` |
|-----|-------------------|-------------------------|
| **`p`** | A **person / Nostr identity**: the subject is a **public key** (secp256k1 x-only, on the wire as **64 lowercase hex characters** in the tag value). | The `p` tag value: **64 lowercase hex characters** (same string as on the wire). |
| **`i`** | A **typed subject id** covering Nostr references, hashes, URLs, and external ids. | The full normalized `i` value (for example `nostr:event:<value>`, `nostr:note:<value>`, `nostr:pubkey:<value>`, `nostr:profile:<value>`, `nostr:addr:<value>`, `hash:<hex>`, `web:<normalized-url>`, `ext:<external-id>`). |

**Note:** For Nostr-typed `i` values, implementations MAY ingest either 64-hex or NIP-19-encoded values (when available), but SHOULD canonicalize consistently before computing `d`.

#### Step 2 — Per-subject fragment (always 64 lowercase hex characters)

For each subject:

* If `P` matches **exactly** `^[a-fA-F0-9]{64}$` (64 hex digits, any case before lowercasing), the **fragment** `F` is `P` in **lowercase** (no hashing).
* Otherwise, `F = lowercase_hex(SHA256(UTF8_bytes(P)))` (64 hex characters).

So for a **`p`** subject, **`d_base`** equals the **`p` tag value** (same 64-character lowercase hex string). Most typed `i` values (event refs, hashes, URLs, external ids, etc.) use a **hash** of `P`, giving a fixed-width fragment.

#### Step 3 — Combine fragments

Fragments `F₁ … Fₙ` correspond to subjects `S₁ … Sₙ` in **wire tag order** (see **[Multiple subjects (batch)](#multiple-subjects-batch)**).

1. **Deduplicate:** Let `U = (U₁, …, Uₘ)` be `F₁ … Fₙ` with **duplicate 64-hex strings removed**: scan in order; append `Fᵢ` only if no earlier fragment equals `Fᵢ` (string equality on the lowercase hex). Thus `m` is the count of **distinct** fragments; `m ≥ 1` when `n ≥ 1`.

2. **Combine:**
   * **One unique fragment (`m = 1`):** `d_base = U₁`.
   * **Several unique fragments (`m > 1`):** Hex-decode each `Uⱼ` to 32 bytes. Let `B = B₁ ⊕ B₂ ⊕ … ⊕ Bₘ` (bitwise XOR per byte). `d_base` is `B` encoded as **64 lowercase hex characters**. XOR is commutative, so the **value** of `d_base` does not depend on XOR evaluation order among the unique fragments.

#### Step 4 — Context suffix

* If there is **no** context, or context is the empty string, `d = d_base`.
* If context is a **non-empty** string `C`, `d = d_base + "|" + C` (literal ASCII `0x7C`). The same `C` MUST appear in the `c` tag when using contextual trust.

#### Implementation checklist

* Use **UTF-8** encoding for `SHA256` input when `P` is not raw hex.
* Output hex is **lowercase**.
* For `nostr:*` values, canonicalize `<value>` consistently before computing `d`.
* **Deduplicate** fragments before XOR (see Step 3) so duplicate subjects cannot forge a `d` via cancellation.
* For golden tests, fix `P` for a few examples and compare `F` and `d` across implementations.

### Contexts (`c` tag)

Trust is rarely absolute; it is contextual. The `c` tag allows authors to specify the domain.

**Context strings are arbitrary.** Users and communities are free to define their own contexts (e.g., "rocket-science", "cooking", "moderation"). However, to maximize interoperability and discoverability, it is **strongly advised** to reuse existing, well-known context terms where applicable.

Common contexts:
*   `""` (Empty string) or omitted: Default. General character/identity trust.
*   `"development"`: Competence/safety in writing code.
*   `"security"`: Trustworthiness in security audits.
*   `"commerce"`: Reliability in trading/payments.
*   `"nostr"`: Good actor in the Nostr network (anti-spam).

### Trust Values (`v` tag)

*   **`1` (Trust):** "I vouch for this subject in this context. Their actions/content are beneficial."
*   **`0` (Neutral):** "I have no strong opinion, or I am revoking a previous rating." This effectively removes the edge from the graph.
*   **`-1` (Distrust):** "I explicitly distrust this subject. Their actions/content are harmful or malicious."

### NIP-73 Integration

[NIP-73](https://github.com/nostr-protocol/nips/blob/master/73.md) defines external content IDs using `i` and `k` tags. Trust events MAY assert trust on these identifiers (e.g. books via ISBN, papers via DOI, podcasts via GUID, blockchain transactions). Clients can query `kind:32010` events filtered by `i` or `k` tags to discover trust assertions for a given external content ID. The `i` tag value MUST follow NIP-73 format and normalization rules (lowercase where specified, no hyphens for ISBN/ISAN, etc.).

## Client Behavior (Recommendation)

Clients SHOULD use these events to construct a **local trust graph**:

1.  **Sync:** Fetch all `kind:32010` events from the user's followed/trusted authors.
2.  **Resolve:** For each author, process events in chronological order (`created_at`).
    *   **Validity window:** When building the graph, consider only events that are currently valid for resolution. If the event has an `x` (activate) tag, include it only when current time **≥** that timestamp. If it has a `y` (expire) tag, include it only when current time **≤** that timestamp. If the event has one or more `z` (schedule) tags, include it when the current time falls within at least one such window: for each `z`, the window starts at the last cron occurrence at or before the current time and lasts for the given duration in seconds. Cron is evaluated in UTC. If both `x`/`y` and `z` are present, all conditions apply (e.g. within `x`–`y` and within a `z` window). Events without `x`, `y`, or `z` are always valid.
    *   **Latest Wins:** If multiple events from the same author assert trust on the same **subject AND context** (regardless of `d` tag or batching), the assertion with the latest timestamp OVERRIDES all previous ones.
    *   **`nostr:pubkey` behavior:** Trust to `i=nostr:pubkey:<value>` is counted toward that pubkey’s trust score, but this subject type is **not** used as a graph-expansion/follow edge during path resolution. It contributes to scoring only.
    *   **Context Scope:** Assertions in different contexts (e.g., "coding" vs "trading") are independent and do not override each other.
    *   **Example:** An author publishes a batch event trusting `A` and `B` in "coding" at `t1`. Later, they publish a single event distrusting `A` in "coding" at `t2`. The client's final state for that author is: Trust `B` (coding), Distrust `A` (coding).
3.  **Compute:** Calculate an aggregate reputation score for any target based on the weighted paths from the user.
4.  **Filter:** Hide content or warn users about subjects with a net-negative trust score.

## Security Considerations

*   **Sybil Attacks:** A reputation system based on *subjective* graphs (starting from the user's own trust root) is naturally resistant to Sybil attacks.
*   **Privacy:** Trust ratings are public. Users should be aware that publishing a `-1` rating is a public statement of distrust.
